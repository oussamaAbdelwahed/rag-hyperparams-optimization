1. ### <a name="_mv05d4jab9mm"></a><a name="_q60zfuhiltbr"></a>**Comportement**
**Dynamisme du Menu :**

Deux états du menu latéral sont disponibles :

- Etat  réduit : avec uniquement les icônes.
- Etat développé : avec les titres des menus et leurs icônes respectives. 

Le menu latéral de navigation sera toujours réduit par défaut et se développe dans deux scénarios :

- Survol de la souris : Lorsque le curseur survole le menu, celui-ci s'ouvre et reste ainsi tant que le curseur demeure sur lui. Si le curseur quitte la zone, le menu retrouve son état réduit.
- Interaction avec le "Burger Menu" : En cliquant sur le "Burger Menu", le menu se développe et reste figé dans cet état. Il revient à son état rétréci uniquement si l'utilisateur clique à nouveau sur le "Burger Menu", actualise la page, ou navigue vers une autre interface.

**Niveau et principes des sous-menus :** 

Le menu latéral pourra contenir jusqu'à deux niveaux différents de sous-menus. Par exemple, dans le sous-menu "Gestion des utilisateurs", vous trouverez deux sous-menus de deuxième niveau : "Gestion des utilisateurs Clients" et "Gestion des utilisateurs Portail".

Les sous-menus sont par défaut fermés et s'ouvrent verticalement au clic, suivant la logique d'un menu déroulant. Si un sous-menu de deuxième niveau est sélectionné, le menu latéral affichera ce sous-menu développé et ne se réduira que lorsque vous naviguez vers une autre interface d'un autre menu.

**Marqueur de position :** 

Pour distinguer les niveaux, deux colorations différentes sont disponibles : 

- Une première pour le sous menu de premier niveau
- Une deuxième pour le sous menu de deuxième niveau

Lorsque L'utilisateur est sur un sous-menu de deuxième niveau, un marqueur indiquera la sélection sur le sous-menu de premier niveau, ainsi qu'un deuxième marqueur pour le sous-menu de deuxième niveau sélectionné.

1. ## <a name="_fy3oz4xcp4q0"></a>Le Listing
   1. ### <a name="_ahaodcitzy1e"></a>**La barre de recherche**
**Principes** : 

La barre de recherche intégrée au listing permet d'effectuer des recherches sur l'ensemble des colonnes présentes.

La recherche est basée sur le principe du **"contient exactement le champ"**, ce qui signifie que seuls les résultats correspondant exactement aux critères spécifiés saisies seront affichés. 

- A titre d’exemple, la saisie du mot “alexandre” permettra d’afficher uniquement les lignes pour lesquelles la valeur alexandre est présente dans au moins une colonne. 

**Comportement** :

Le bloc de recherche applique un filtrage automatique dès que l'utilisateur commence à saisir des caractères. Il n'est pas nécessaire de cliquer sur "Entrer" pour démarrer l’affichage des résultats dans le listing.

1. ### <a name="_cpsp4482ykfp"></a>**Les colonnes et les lignes du listing**
**Dynamisme des colonnes :**

Les colonnes du listing sont dynamiques, permettant aux utilisateurs de personnaliser leur position selon leurs préférences.

Cependant, il est important de noter que ces modifications de position ne sont pas enregistrées indéfiniment :

- La personnalisation des colonnes est conservée lorsque l’utilisateur navigue sur le middleware entre les différentes interfaces.
- A la déconnexion du back-office ou à l’expiration de la session, les colonnes retrouveront leur position par défaut.

**Tri par colonne :**

Un tri est proposé par défaut sur chaque colonne, offrant plusieurs types de tri en fonction des informations affichées. Les types de tri disponibles incluent:

- Alphabétique (Croissant / Décroissant)
- Chronologique (Croissant / Décroissant)
- Ordre numérique (Croissant / Décroissant)

Le tri est activé en cliquant sur l'en-tête de la colonne souhaitée. Un deuxième clic sur la même en-tête inversera l'ordre du tri.

**Actions sur les lignes :**

La seule action possible sur les lignes du tableau est l’accès au détail de la ligne. Cet accès est possible avec un double clic sur la ligne. (toute la ligne est cliquable).

- A titre d’exemple : Si l'utilisateur se trouve sur la "Liste des utilisateurs XL EDS" et clique sur la ligne de l'utilisateur "Alexandre", il sera redirigé vers l'interface "Fiche utilisateur Alexandre".

1. ## <a name="_nzsd1bd5e3hf"></a>Le filtre générique du Listing
   1. ### <a name="_e1y7apx4hctr"></a>**Apparence**
![](Aspose.Words.40e8c1a8-ff93-4ff9-88e2-19e04c03a199.005.png)
1. ### <a name="_h175npdlmwv8"></a>**Comportement**
Accessible sur toutes les listes du back-office, le filtre est présenté sous la forme d'une popin. Ce filtre permet d'appliquer des critères de filtrage sur toutes les colonnes du listing.

Les utilisateurs peuvent effectuer plusieurs combinaisons de critères de filtrage au sein du même niveau du filtre, en utilisant les options "OU" et "ET" pour affiner leur filtre.

**Processus de Filtrage et critère de filtrage**

Pour définir un critère de filtrage, l’utilisateur doit :

- Sélection de la colonne : L'utilisateur commence par choisir la colonne cible sur laquelle il souhaite appliquer le filtrage.
- Choix de l'Action : Ensuite, il sélectionne une action possible à partir d'une liste déroulante, en fonction du type de données affichées dans la colonne choisie.
- Saisie de la valeur recherchée en fonction de l’action choisie

**Les combinaisons des Critère de filtrage :** 

L'utilisateur a la possibilité de combiner plusieurs critères de filtrage à l'aide des combinaisons "**ET**" et "**OU**". Voici comment cela fonctionne :

- Combinaison "ET" : Tous les critères de filtrage définis doivent être respectés par les données filtrées. (exemple : critère 1 et  critère 2 et … et critère N). Cela correspond à une intersection des valeurs
- Combinaison "OU" : Un seul critère doit être respecté par les données filtrées. Cette option permet de récupérer un ensemble de données plus large, en incluant celles qui satisfont au moins l'un des critères spécifiés. (exemple : critère 1 OU critère 2 OU … OU critère N). Cela correspond à l’union des valeurs. 

**A noter** : Il est important de noter que sur un même niveau, l'utilisateur peut utiliser différentes combinaisons de filtrage. Cela signifie qu'il peut mélanger les deux types de combinaisons sur le même niveau. Par exemple, il peut définir certains critères avec "ET" tout en ayant d'autres critères avec "OU".

**Actions possibles par type de données**

- Données de type “**Texte**” : 
  - Action “Contient”
  - Action  “Vide”
  - Action “Se termine par”
  - Action “Égale à”
  - Action “Pas égale à”
  - Action “Ne contient pas”
  - Action “Pas vide”
  - Action “Ne se termine pas par”
  - Action “Ne commence pas par”
  - Action “Commence par”

- Données de type “**Date**” : 
  - Action “Après le”
  - Action “Avant le”
  - Action “Entre”
  - Action “Vide”
  - Action “Égale à”
  - Action “Pas égale à”
  - Action ”Pas entre”
  - Action “Pas vide”

- Données de type “**Nombre**” :
  - Action “Entre”
  - Action “Vide”
  - Action “Égal à”
  - Action “Supérieur à”
  - Action “Supérieur ou égal à”
  - Action “Inférieur à”
  - Action 'Inférieur ou égal à”
  - Action “Pas égal à”
  - Action “Pas entre”

1. ## <a name="_fbattzcjv742"></a>Fonctionnalité “Flux URBANTZ (Client HTTP Urbantz)”
   1. ### <a name="_vvp9trbahs5h"></a>**Notions clés et configurations URBANTZ**
      1. #### <a name="_ii8ty71iyftb"></a>*Commandes / Tâches*
Pour XL EDS, deux types de commandes existent :

- Commande de distribution
- Commande de collecte

L’annonce de ces commandes sur Urbantz, se fait via les tâches suivantes :

- Tâche de "Delivery"
- Tâche de "Pickup"

En règle générale, chaque commande est représentée par une seule tâche sur Urbantz. Toutefois, dans certains cas, une commande peut être traduite en deux tâches "Pickup/Delivery", qui sont alors liées entre elles par l’attribut “taskId” qui sera le même pour les deux tâches.

Les données de mapping sont définies dans ce [fichier de mapping](https://docs.google.com/spreadsheets/d/1_HrjjJNjlvldl6bBtgzk01deVXXrq-hMwG7WGh2shYc/edit?gid=0#gid=0). Les attributs grisés sont hors scope, tandis que les données "requires" seront gérées exclusivement par Urbantz, car elles concernent la manipulation du PDA, ce qui les place hors du périmètre du middleware XL EDS aussi.

1. #### <a name="_4gcigol04gqp"></a>*Les “Métadonnées”*
Les métadonnées dans Urbantz sont utilisées pour effectuer un paramétrage personnalisé de la plateforme. Sur Urbantz, on a trois types de métadonnées :

- Métadonnée liées à l'article
- Métadonnée liées à la tâche
- Métadonnée liées à la tournée

Dans  l’annonce d’une tâche, uniquement la métadonnée “store” sera annoncée pour préciser le magasin donneur d'ordre, toutes les autres métadonnées configurées dans la plateforme seront à consommer, plus tard, dans les flux entrants (Webhooks) lors de l'acheminement de la commande.

voici [la liste des métadonnées](https://docs.google.com/spreadsheets/d/1MTiCry-bal8MXaV9_-8g7qBJgbqmRRO7/edit?gid=1011767878#gid=1011767878) (voir onglet “metadata configurées”).

L’optimisation représente l'une des configurations d'Urbantz. Dans le cadre du cas XL EDS, elle se réfère aux différentes prestations offertes par XL EDS à ses clients. 

Ces prestations sont les suivantes :

- Prestation ECO
- Prestation J+1
- Prestation EXPRESS

L’optimisation dans Urbantz a pour objectif d'optimiser la création des tournées de livraison à l'aide d'un algorithme d'optimisation. Cet algorithme répartit les commandes correspondant à une optimisation sur plusieurs tournées.

1. ### <a name="_htovcoqigyny"></a>**EPIC :  “API Urbantz - Flux sortant”**
   1. #### <a name="_c1n6uy92mtwk"></a>*Description générale*
Cette EPIC concerne l'implémentation et la gestion des flux sortants vers l'API Urbantz, permettant l'envoi de données depuis le middleware vers Urbantz. Elle a pour objectif de définir les différents flux d'échanges techniques permettant de transmettre les données des commandes de livraison à Urbantz sous forme de:

- Annonce de nouvelle commande de livraison
- Modification de commande de livraison
- Annulation de commande de livraison
- Replanification de commande de livraison

1. #### <a name="_r5ub3b38cxul"></a>*Authentification et configuration des flux de données*
Nous allons utiliser la méthode d'authentification en API KEY sur l’API Urbantz, pour cela, il faut utiliser deux clés dans l’entête de chaque requête API que nous envoyons à Urbantz :

- X-API-KEY: la clé globale générée par plateforme Urbantz, la plateforme XL EDS dans notre cas.
- X-API-SECRET: la clé spécifique générée par Flux de données sur Urbantz

Chaque prestation XL EDS est représentée par une optimisation dans Urbantz et pour chaque magasin une optimisation doit être créée et configurée spécifiquement.

Un flux de données est créé et configuré au niveau de chaque optimisation préalablement créée sur Urbantz, pour obtenir la clé spécifique à utiliser dans les requêtes API.

**=> Nous aurons donc dans Urbantz, un flux par optimisation par magasin**

1. #### <a name="_gcy4nn33bor"></a>*Détails des Tâches*
1  ##### <a name="_wj7c374w0yvl"></a>*TSK- Annonce d'une tâche de commande de livraison*
Chaque nouvelle commande de livraison reçue par le middleware génère une annonce de tâche(s) correspondante(s) dans Urbantz. Selon le type de commande (du point de vue métier), l'annonce de la tâche est traitée différemment par l'API Urbantz, de la manière suivante:

1. Distribution simple (récupération des colis à l'adresse principale du magasin / Hub)

C’est le cas nominal le plus simple, nous allons annoncer pour ce cas une seule Tâche de type “delivery” sur Urbantz en précisant l’identifiant Urbantz du magasin donneur d’ordre dans la métadonnée “store” et l’adresse du client final dans l’adresse d’annonce.

Le service de “reprise recyclage”  est considéré comme un service additionnel à la tâche de distribution simple. 

1. Distribution adresse différente (récupération des colis à l'adresse secondaire ou autre magasin)

C’est le cas où l’adresse de récupération des colis est différente de l’adresse principale du magasin donneur d’ordre, elle peut être une adresse secondaire du magasin donneur d’ordre ou une adresse d’un autre magasin.

Pour ce cas nous allons annoncer deux Tâches sur Urbantz:

1: Tâche de collecte de type “pickup”: dans cette tâche nous allons renseigner l’identifiant Urbantz du magasin donneur d’ordre dans la métadonnée “store” et l’adresse secondaire ou du magasin d’où se fera la récupération des colis dans l’adresse de l’annonce.

2: Tâche de distribution de type “delivery”: dans cette tâche nous allons renseigner l’identifiant Urbantz du magasin donneur d’ordre dans la métadonnée “store” et l’adresse du client final dans l’adresse de l’annonce.

**NB:** 

- Les deux tâches doivent avoir le même identifiant de tâche (champ “taskId”), le même créneau de livraison (champ “timeWindow”) et des colis identiques (champ “Items”)
- Le service d’échange ne peut pas être associé à une tâche de distribution adresse différente. Tout échange doit être fait au niveau du magasin donneur d’ordre. 

1. Distribution avec service additionnel de livraison en point relais

C’est le cas où le client final voudrait se faire livrer dans un point relais, ce cas est identique au premier cas nominal de distribution simple avec comme adresse de l’annonce l’adresse du point relais (autre magasin) mais avec un champ supplémentaire dans l’annonce qui est l’identifiant du service dans Urbantz dans le champ “categories” pour préciser que c’est à livrer dans un magasin et non pas à l’adresse du client final.

Si l’adresse de récupération des colis à livrer est différente de l’adresse principale du magasin donneur d’ordre alors nous devons créer deux tâches comme le cas de distribution adresse différente.

1. Collecte (Commande retour)

Pour toutes les commandes de type collecte, qu’elles concernent un retour à l’adresse principale du magasin donneur d’ordre ou à une autre adresse (adresse secondaire du magasin donneur d’ordre ou adresse d’un autre magasin), deux tâches seront annoncées sur Urbantz :

1: Tâche de collecte de type “pickup”:  dans cette tâche nous allons renseigner l’identifiant Urbantz du magasin donneur d’ordre dans la métadonnée “store” et l’adresse du client final dans l’adresse de l’annonce.

2: Tâche de distribution de type “delivery”: dans cette tâche nous allons renseigner l’identifiant Urbantz du magasin donneur d’ordre dans la métadonnée “store” et l’adresse du magasin où il faudra retourner les colis dans l’adresse de l’annonce.

**NB:**

- Les deux tâches doivent avoir le même identifiant de tâche (champ “taskId”), le même créneau de livraison (champ “timeWindow”) et des colis identiques (champ “Items”)
- Le service d’échange est considéré comme un service additionnel associé aux deux tâches “Collect/distri” du retour de la commande de type échange.
- Toutes les commandes de type retour doivent être annoncées en leur attribuant le service additionnel "Retour merchandise", sauf pour les commandes de type échange, pour lesquelles seule le service additionnel "Échange merchandise" leur sera associé.

**Remarque Générale :** 

Il est à noter que toutes les commandes reçues par le middleware contiennent toujours une seule adresse de collecte et une seule adresse de livraison pour l’ensemble des colis. 

Le middleware ne gère pas des commandes incluant plusieurs adresses de collecte ou de livraison avec une association d’un sous-ensemble de colis spécifique. 
1  ##### <a name="_t0ocd8ugqdtj"></a>*TSK- Modification d'une tâche de commande de livraison*
Chaque commande peut être modifiée à tout moment de son cycle de vie jusqu’à ce que la tournée à laquelle elle est affectée soit démarrée (voir section webhook récupération des informations d’une tournée).

Certaines données de la commande peuvent être modifiées dans les étapes du processus de livraison mais pas dans d’autres étapes, ces données et les règles de gestion métier qui autorisent ou pas la modification seront fournies par l’équipe Urbantz ultérieurement.

Lors de la modification d'une d'une commande via l'API Urbantz il faut utiliser la méthode UPDATE, cette méthode implique de remplacer la ressource entière par les nouvelles données. Concrètement, cela signifie qu'il est nécessaire d'envoyer l'intégralité des données de la tâche, même si seule une partie des informations change. En d'autres termes, toutes les propriétés de la tâche doivent être envoyées à l’API Urbantz, même celles qui ne sont pas modifiées.

De la même manière que l’annonce, la modification d’une tâche dans Urbantz est gérée différemment selon le cas de création commande.

Si dans une modification d’une commande de livraison, le créneau de livraison est modifié, cela génère une requête de re-planification à part (voir plus bas dans la section re-planification).

1  ##### <a name="_eftxgw7q2m3x"></a>*TSK- Annulation d'une tâche de commande de livraison*
Chaque commande peut être annulée à tout moment du processus de livraison tant que la tournée n’a pas démarré. L’annulation se traduit par une requête de “discard” dans l’API Urbantz, seule l’identifiant de la tâche est nécessaire comme paramètre pour cette requête.

1  ##### <a name="_6ro4ptwplwdt"></a>*TSK- Replanification d'une tâche de commande de livraison*
La modification du créneau de livraison d’une commande est gérée séparément et de façon dédiée dans une requête de “replan”, cette requête est différente de la requête de modification et permet d’envoyer seulement le créneau à modifier et ne nécessite pas d’envoyer l'intégralité des données de la tâche.

Comme pour la requête de modification et de l'annulation, la re-planification d’une tâche est possible à tout moment du processus de livraison tant que la tournée n’a pas démarré.

1  ##### <a name="_ji6mbpvzje9i"></a>*TSK- Réception des données d’une tâche urbantz*
Pour récupérer les données d’une tâche tout au long du processus de livraison, il faut s’abonner aux webhooks suivants:

- TaskAnnouced: ce webhook se déclenche lorsqu’une tâche a été annoncé dans Urbantz et permet de récupérer le statut initial (PENDING) de la commande avec toutes les données envoyé lors de l’annonce et aussi ajoutées et pré-calculées automatiquement par Urbantz au moment de l’annonce.
- TaskStatusChanged: ce webhook se déclenche à chaque modification de statut d’une tâche (hors création/annonce) et renvoie toutes les données de la tâche. Il faut savoir que ce webhook peut se déclencher en même temps que le webhook TaskChanged quand il y a une modification des données de la tâche accompagnée par un changement de statut.
- TaskChanged: ce webhook se déclenche à chaque modification dans les données de la tâche (hors statut) et renvoie toutes les données de la tâche.

1  ##### <a name="_3it57754fdus"></a>*TSK- Récupération des informations d’un véhicule*
Pour récupérer les données d’un véhicule, il faut s’abonner au webhook de la tournée. Les données du véhicule assigné à une tournée sont ajoutées à la tournée au moment où le véhicule est assigné et peut être récupéré dans chacun des webhooks de la tournée (voir section suivante).

1  ##### <a name="_eczxn09sp5qk"></a>*TSK- Récupération des informations d’une tournée*
Pour récupérer les données d’une tournée il faut s’abonner au webhook suivants:

- round.validated: ce webhook se déclenche au moment où l’optimisation dans Urbantz est validée (automatiquement ou manuellement), à la réception de ce webhook un email est envoyé au client donneur d’ordre avec le planning de la tournée validée.
- round.ongoing: ce webhook se déclenche quand le chauffeur indique sur son PDA qu’il a démarré sa tournée. Toutes les commandes des tâches associées à cette tournée ne seront plus modifiables ni annulables à partir de cet instant.
- round.completed: ce webhook se déclenche au moment où le chauffeur indique qu’il a fini sa tournée.

     1. ### <a name="_93f1uzbmo8vv"></a>**EPIC :  “Standard API”**
        1. #### <a name="_uq390ui0xj11"></a>*Description générale*
Cette EPIC concerne la conception et l'implémentation de la "Standard API", qui constitue le socle du middleware XL EDS. La Standard API définit le modèle standard de gestion des commandes au sein du middleware et gère tous les flux des commandes, qu'elles proviennent directement de l'API (à travers le Portail de commande) ou via des intégrations spécifiques aux différents systèmes WOOP et Centiro.

Toutes les demandes de création, re-planification, modification, annulation de commande ou demande de devis transitent par la standard API. Cette API permet de convertir toutes les requêtes en un format standardisé pour le middleware, avant de les transmettre au client HTTP Urbantz pour qu'elles soient envoyées à Urbantz.

Cette EPIC détaille les règles métier et les critères de gestion, ainsi que les conditions d'acceptation ou de rejet des requêtes reçues par le système.
1. #### <a name="_642r04qgpazf"></a>*Authentification de la “Standard API”*
La standard API est sécurisée et l'accès est contrôlé via un mécanisme d'authentification basé sur une clé d'API. Chaque expéditeur dispose d'une clé API unique, qui doit être envoyée dans l'en-tête X-API-KEY de chaque requête.

Cette clé permet d'identifier l’expéditeur à lequel appartient le magasin donneur d’ordre et de garantir que seules les requêtes autorisées peuvent accéder aux ressources de l'API. De plus, il est possible de régénérer chaque clé API à tout moment.

1  ##### <a name="_sur0l06ydtfl"></a>*US- Gestion du temps de service d’une commande depuis la STANDARD API*
- Lors de la réception d'une nouvelle commande via l'API standard ou de la modification d'une commande existante, le temps de service de la commande doit être calculé et communiqué pour chaque tâche Urbantz associée à cette commande.
- Le calcul de l’attribut « temps de service » s’effectue pour chaque commande reçue via l'API standard, en prenant en compte les critères suivants :
  - Temps de « Collecte » du colis
  - Temps du « Service de base » :
    - Livraison au pied du camion
    - Pièce du choix avec ascenseur
    - Pièce du choix sans ascenseur
    - Échange de marchandise
    - Retour de marchandise
    - Passage à 4
    - Livraison en point relais
  - Temps des « Services additionnels » :
    - Mise en service
    - Montage simple
    - Montage complexe
    - Reprise recyclage

- La liste des temps de service pour chaque service est présente dans ce document”[Temps de service - XL EDS](https://docs.google.com/spreadsheets/d/1ln3FqaaLoHMA5QCl-s8EyMZqseMm7Oja/edit?gid=656508273#gid=656508273)".
- Lors de l’annonce des tâches sur Urbantz, le temps de service de chaque tâche créée lui sera affecté automatiquement par le middleware. Plusieurs scénarios peuvent se présenter :



**1/- Commande avec une tâche de “Distribution simple” :**

- La formule de calcul pour une tâche de distribution simple est la suivante :

**Temps de service d’une tâche**

**=**

**Temps de service de base + Temps des services additionnels**

- Remarque : Le temps de collecte n'est pas ajouté pour une tâche de distribution simple.

**2/- Commande composée de deux tâches de « Collecte/Distribution » :**

- Chaque tâche de la commande a un temps de service spécifique calculé séparément dans le système.
- Pour déterminer le temps de service total de la commande sur le middleware, on additionne les temps de service des différentes tâches.
- La formule de calcul pour le temps de service de la commande :

**Temps de service de la commande**

**=**

**Temps de service de la tâche Collecte + Temps de service de la tâche Distribution**

- La formule de calcul pour le temps de service de la tâche de collecte :

**Temps de service de la tâche Collecte**

**=**

**Temps de collecte + Temps de service de base + Temps des services additionnels**

- La formule de calcul pour le temps de service de la tâche de distribution :

**Temps de service de la tâche** 

**=**

**Temps de service de base + Temps des services additionnels**

- **Remarque** : Le temps de collecte est uniquement calculé pour les commandes où la collecte a lieu dans un magasin, et non pour les collectes des commandes retour ou échange (Collecte chez l’adresse du client consommateur).
1  ##### <a name="_a3cl4zm1wce"></a>*US- Création d'une commande depuis la STANDARD API*

**Diagramme : Workflow de création de commande**

![](Aspose.Words.40e8c1a8-ff93-4ff9-88e2-19e04c03a199.010.png)



À la réception d’une nouvelle commande sur le middleware XL EDS, plusieurs vérifications doivent être effectuées afin que la commande soit validée, créée sur le middleware, puis envoyée à Urbantz.

Le diagramme ci-dessus schématise les règles d’acceptation et de rejet d'une demande de création de commande via la Standard API. Ces règles définissent les conditions sous lesquelles la commande sera acceptée ou rejetée, en fonction des critères métier et des validations nécessaires à chaque étape du processus.

**Règles de validation et de rejet des demande de création de commandes :**

Pour qu’une nouvelle commande soit créée sur le middleware XL EDS, plusieurs vérifications et validations doivent être effectuées sur les commandes clients. Voici l’ordre précis des règles métier pour l’acceptation des nouvelles commandes sur le middleware :

*1/ - Vérification du “**Statut du magasin**”*

Sur le middleware, les magasins donneurs d’ordre peuvent avoir l’un des deux statuts suivants :

- Actif : Le magasin peut envoyer des commandes.
- Inactif : Le magasin ne peut pas envoyer de commandes.

Lors de la réception d’une nouvelle commande, le statut du magasin est vérifié selon les règles suivantes :

- Acceptation de la commande : Si le magasin est actif, alors la commande est acceptée et passe à la vérification suivante.
- Rejet de la commande : Si le magasin est inactif, alors la commande est rejetée.

*2/ - Vérification de la “**Référence client de la commande**”*

Lors de la réception d’une nouvelle commande, le middleware contrôle la référence client de la commande,afin d’éviter les doublons, selon les règles suivantes :

- Acceptation de la commande : La commande est acceptée si : 
  - La référence client **n’existe pas encore** sur les commandes du magasin concerné,
  - La référence client existe déjà, mais uniquement sur des commandes ayant l’un des statuts suivants :
    - Annulation XL EDS
    - Annulation client
    - Annulation client tardive
    - Annulation client après chargement

Dans ce cas, la commande poursuit le processus de vérification.

- Rejet de la commande : La commande est rejetée si une autre commande du même magasin possède **exactement la même référence client** mais avec un **statut différent** de ceux listés ci-dessus.

*3/ - Vérification des “**Jours Off**”*

Des jours off sont définis sur le middleware XL EDS, durant lesquels les services de transport sont suspendus. À la réception d’une nouvelle commande, la première vérification concerne ces jours off, selon les règles suivantes :

- Acceptation de la commande : Si la date de “Livraison de la commande” est en dehors des "Jours Off XL EDS", alors la commande est acceptée et passe à la vérification suivante.
- Rejet de la commande : Si la date de “Livraison de la commande” coïncide avec un "Jour Off XL EDS", alors la commande est rejetée.

Les jours Off XL EDS implémentés sur le système sont :

- Le 25 Décembre
- Le premier Janvier
- Le premier Mai

*4/ - Vérification de la “**Prestation de la commande**”*

Lors de cette étape, le middleware effectue une vérification de la prestation associée à la commande afin de déterminer si celle-ci peut être acceptée ou doit être rejetée.

- Acceptation de la commande : Si la prestation de la commande figure parmi la liste des prestations dont le magasin donneur d’ordre est bénéficiaire, alors la commande est acceptée et passe à la vérification suivante.
- Rejet de la commande : Si la prestation de la commande ne correspond à aucune des prestations dont le magasin donneur d'ordre est bénéficiaire, la commande est rejetée.

*5/ - Vérification des “**Paramètres de la commande**”*

L’étape de vérification des paramètres de la commande consiste à vérifier la conformité des données par rapport aux paramètres globaux définis sur le magasin donneur d’ordre de la commande. Quatre Paramètres clés sont vérifiés :

- Le “Poids maximal par colis”
- La “Hauteur maximale par colis”
- La “Largeur maximale par colis”
- La “Longueur maximale par colis”

Les règles métier pour cette vérification sont les suivantes :

- Acceptation de la commande : La commande est acceptée si les critères suivants sont respectés :
  - Le poids de chaque colis de la commande ne dépasse pas la valeur limite définie dans les paramètres du magasin.
  - La hauteur de chaque colis de la commande ne dépasse pas la valeur limite définie dans les paramètres du magasin.
  - La largeur de chaque colis de la commande ne dépasse pas la valeur limite définie dans les paramètres du magasin.
  - La longueur de chaque colis de la commande ne dépasse pas la valeur limite définie dans les paramètres du magasin.
- Rejet de la commande : Si l'une des conditions ci-dessus n'est pas respectée, la commande sera rejetée par le système.

**Remarque :**

Si l'une ou plusieurs des valeurs (poids maximal, hauteur maximale, largeur maximale ou longueur maximale par colis) ne sont pas définies pour le magasin donneur d’ordre, il n'y aura pas de vérification par le middleware.

*6/ - Vérification des “**Créneaux de livraison**”*

La vérification des créneaux de livraison se fait par la comparaison de la date de livraison de la commande, communiquée sous un format de plage horaire, avec les créneaux de livraison paramétrés sur le magasin donneur d’ordre.

La règle métier appliquée pour cette vérification est la suivante :

- Acceptation de la commande : si la plage horaire correspond exactement à l’un des créneaux définis, alors la commande est acceptée et passe à la vérification suivante.
- Rejet de la commande : Si la plage horaire de la date de “Livraison de la commande” ne correspond à aucun des créneaux de livraison définis pour le magasin donneur d’ordre, la commande est rejetée.

*7/ - Vérification du “**Cut Off**”*

Une fois que le créneau de livraison a été précisé pour la commande, la vérification du respect du "Cut Off" est effectuée. 

Cette vérification se déroule comme suit :

- Acceptation de la commande : Si l’heure de la “Réception de la commande” ne dépasse pas l’heure du “Cut Off” définie pour le créneau de livraison de la commande, alors la commande est acceptée et passe à la vérification suivante.
- Rejet de la commande : Si l’heure de “Réception de la commande” est après l’heure du “Cut Off” définie pour le créneau de livraison de la commande ou elles sont exactement les mêmes, alors la commande est rejetée.

*8/ - Tarification et application de la grille tarifaire à la commande*

Une fois que toutes les étapes de vérification ont été validées, la commande est envoyée au module de pricing pour tarification. Une grille tarifaire lui est ensuite appliquée. Dans le cas où la commande est hors grille et ne respecte pas les dimensions de celle-ci, la demande de création de la commande sera rejetée.

**Annulations Client :**

Pour ce type d’annulation, dès la réception des demandes via la Standard API, plusieurs vérifications doivent être effectuées avant d’effectuer l’annulation de la commande.

Le premier diagramme schématise les règles d’acceptation et de rejet d'une demande d’annulation. Ces règles définissent les conditions sous lesquelles l’annulation sera acceptée ou rejetée, en fonction des critères métier et des validations nécessaires à chaque étape du processus.

Voici l’ordre précis des règles métier pour l’acceptation des demandes d’annulation de commandes :

*1/ - Vérification de “**La référence de la commande**”*

À la réception d’une demande d’annulation, la première vérification concerne la référence de la commande sur le middleware, selon les règles suivantes :

- Acceptation de la commande : Si la référence de la commande existe sur le système, alors la demande d’annulation est acceptée et passe à la vérification suivante.
- Rejet de la commande : Si la référence de la commande n'existe pas sur le système, alors la demande d’annulation est rejetée.

*2/ - Vérification du “**Magasin donneur d’ordre**”*

À la réception d’une demande d’annulation, le magasin declenchant la demande d’annulation est vérifié selon les règles suivantes :

- Acceptation de la commande : Si l’identifiant communiqué est le même que celui du magasin donneur d’ordre de la commande cible, alors la demande d’annulation est acceptée et passe à la vérification suivante.
- Rejet de la commande : Si L’identifiant communiqué ne correspond **pas** à celui du magasin donneur d’ordre de la commande cible, alors la demande d’annulation est rejetée.

*3/ - Vérification du “**Statut de la commande**”*

À cette étape, le middleware procède à la vérification du statut de la commande. Les règles métier pour cette vérification sont les suivantes :

- Si le statut de la commande est l’un des statuts suivants : 
- Annulation Client
- Annulation Client tardive
- Annulation Client après chargement
- Annulation XL EDS

` 		`⇒ alors la demande d’annulation est rejetée avec un premier motif de rejet.

- Si le statut de la commande est l’un des statuts suivants : 
- Livrée
- Echec de livraison
- Echec de chargement

` 		`⇒ alors la demande d’annulation est rejetée avec un deuxième motif de rejet.

- Sinon pour tous les autres statuts, la demande d’annulation est acceptée et passe à la vérification suivante .

*4/ - Traitement de la demande “d’annulation de la commande”*

À cette étape, toutes les demandes d'annulation sont acceptées par le middleware. Il est maintenant temps de traiter la demande d'annulation. Le traitement varie en fonction de l'heure du Cut-Off de la commande.

Ainsi, trois scénarios peuvent se présenter :

- **Annulation avant cut off**

Dans le cas où l'heure de réception de la demande d'annulation est antérieure au cut off défini dans la prestation de la commande, l'annulation est traitée directement par le middleware.

Celui-ci modifie le statut de la commande en "**Annulation Client**" et envoie ensuite l'annulation des tâches associées à la commande vers Urbantz via l’API Urbantz.

- **Annulation après cut off et avant chargement de la commande**

Si la demande d'annulation est reçue après l'heure du Cut Off mais avant le chargement de la commande, l'annulation est également prise en charge directement par le middleware.

Celui-ci met à jour le statut de la commande en "Annulation Client tardive" et transmet ensuite l'annulation des tâches associées à la commande vers Urbantz via l'API.

Remarque : 

- Les tâches sont annulées et retirées également de la tournée à laquelle elles étaient affectées.

- **Annulation après le démarrage de la tournée**

Pour les demandes reçues après le chargement de la commande par le livreur, le middleware génère une alerte destinée à l’équipe XL EDS, qui prendra en charge l'annulation directement sur Urbantz.

Dès la réception de l'alerte, l'équipe dédiée contacte le livreur pour lui transmettre l'information, et celui-ci procède à l'annulation de la livraison en sélectionnant le motif "Annulation Client après chargement".

Cette dernière action déclenche un webhook "TaskChanged" envoyé par Urbantz, signalant un échec de livraison avec, dans les raisons d'échec, le motif "Annulation Client après chargement".

À la réception de ce webhook, le middleware met à jour le statut de la commande en "Annulation Client après chargement".

1  ##### <a name="_933vbh2qfxtb"></a>*US- Re-planification d'une commande depuis la Standard API*
**Diagramme : Workflow de replanification de commande**

![](Aspose.Words.40e8c1a8-ff93-4ff9-88e2-19e04c03a199.013.png)

À la réception d’une demande de replanification sur la standard API, plusieurs vérifications doivent être effectuées afin que la replanification soit validée, prise en considération puis envoyée à Urbantz.

Le diagramme ci-dessus schématise les règles d’acceptation et de rejet d'une demande de replanification de commande via la Standard API. Ces règles définissent les conditions sous lesquelles la demande sera acceptée ou rejetée, en fonction des critères métier et des validations nécessaires à chaque étape du processus.

**Règles de validation et de rejet des demande de création de commandes :**

*1/ - Vérification du “**Statut du magasin**”*

Sur le middleware, les magasins donneurs d’ordre peuvent avoir l’un des deux statuts suivants :

- Actif : Le magasin peut replanifier des commandes.
- Inactif : Le magasin ne peut pas replanifier des commandes.

Lors de la réception d’une demande de replanification d’une commande, le statut du magasin est vérifié selon les règles suivantes :

- Acceptation de la demande : Si le magasin est actif, alors la demande de replanification est acceptée et passe à la vérification suivante.
- Rejet de la demande : Si le magasin est inactif, alors la demande de replanification est rejetée.

*2/ - Vérification de “**La référence de la commande**”*

À la réception de la demande, la première vérification concerne la référence de la commande sur le middleware, selon les règles suivantes :

- Acceptation de la commande : Si la référence de la commande existe sur le système, alors la demande de replanification est acceptée et passe à la vérification suivante.
- Rejet de la commande : Si la référence de la commande n'existe pas sur le système, alors la demande de replanification est rejetée.

*3/ - Vérification du “**Statut de la commande**”*

À cette étape, le middleware procède à la vérification du statut de la commande. Les règles métier pour cette vérification sont les suivantes :

- Si le statut de la commande est le statut “Échec de livraison” ou “Échec de chargement” alors la demande de replanification est acceptée et passe à la vérification suivante.
- Si le statut de la commande est tout autre statut alors la demande de replanification est rejetée.


*4/ - Vérification des “**Jours Off**”*

Cette étape concerne la vérification des jours off, selon les règles suivantes :

- Acceptation de la demande : Si la nouvelle date est en dehors des "Jours Off XL EDS", alors la demande est acceptée et passe à la vérification suivante.
- Rejet de la demande : Si la nouvelle date coïncide avec un "Jour Off XL EDS", alors la demande est rejetée.

*5/ - Vérification du “**Créneau de livraison**”*

La vérification du créneaux de livraison se fait par la comparaison de la date de livraison de la commande, communiquée sous un format de plage horaire, avec les créneaux de livraison paramétrés sur le magasin donneur d’ordre.

La règle métier appliquée pour cette vérification est la suivante :

- Acceptation de la commande : si la plage horaire correspond exactement à l’un des créneaux définis, alors la commande est acceptée et passe à la vérification suivante.
- Rejet de la commande : Si la plage horaire de la date de “Livraison de la commande” ne correspond à aucun des créneaux de livraison définis pour le magasin donneur d’ordre, la commande est rejetée.

*6/ - Vérification du “**Cut Off**”*

Une fois que le créneau de livraison a été précisé pour la commande, la vérification du respect du "Cut Off" est effectuée. 

Cette vérification se déroule comme suit :

- Acceptation de la commande : Si l’heure de la “Réception de la commande” ne dépasse pas l’heure du “Cut Off” définie pour le créneau de livraison de la commande, alors la commande est acceptée et passe à la vérification suivante.
- Rejet de la commande : Si l’heure de “Réception de la commande” est après l’heure du “Cut Off” définie pour le créneau de livraison de la commande ou elles sont exactement les mêmes, alors la commande est rejetée.

*7/ - Traitement de la demande de “Replanification de la commande”*

À cette étape, toutes les demandes sont acceptées par le middleware. Il est désormais temps de traiter la demande de replanification, mais une dernière vérification est effectuée afin de déterminer la procédure de traitement à appliquer.

Cette vérification repose sur le **nombre de tâches liées** sur **URBANTZ** et suit les règles métier suivantes:

- Commande de “Distribution simple” : 
  - Si la commande n’a qu’une seule tâche liée sur URBANTZ, qu’elle est de statut autre que “Echec de chargement”, alors la demande de replanification est acceptée.
  - Si la commande n’a qu’une seule tâche liée sur URBANTZ, qu’elle est de statut “Echec de chargement”, alors la demande de replanification est acceptée mais entraîne la réannonce d’une nouvelle tâche.
- Commandes “Retour” et “Distribution complexe” : Si la commande comporte deux tâches liées sur URBANTZ, alors la demande de replanification est également acceptée, mais elle entraîne la réannonce de deux nouvelles tâches sur URBANTZ.

À la réception du webhook, confirmant soit la **replanification réussie** sur **Urbantz**, soit la **création des nouvelles tâches avec succès**, plusieurs mises à jour sont effectuées sur la commande dans le middleware :

- Le statut de la commande devient "Annoncée"
- Le nombre de tentatives de livraison, initialement à n, est incrémenté de 1 (n+1)

1  ##### <a name="_e93fstb8ie19"></a>*US- Gestion des demandes de devis de commande*
**Diagramme : Workflow d’une demande de devis**

![](Aspose.Words.40e8c1a8-ff93-4ff9-88e2-19e04c03a199.017.png)

- Le devis de commande est une entité distincte dans le middleware, gérée indépendamment de la commande elle-même. Contrairement à la commande, il n'existe que sous forme de demande de devis, sans possibilité de modification, annulation, re-planification ou annulation du devis.
- La gestion de devis de commandes consiste à recevoir une demande de devis à travers l'API standard, la traiter et retourner une estimation (Quotation) du prix de livraison de la commande concernée en cas de la validité de la demande.
- Le workflow de gestion de devis suit exactement les mêmes étapes que celui de la création de commande sur le middleware. Il passe par les mêmes processus de vérification, pour finalement aboutir à la génération du devis destiné au clien
- La liste des erreurs et des motifs de rejet des devis est identique à celle détaillée lors de la création de la commande.
- Les clients envoient une demande de devis, et si ce devis est accepté, ils confirment cette acceptation et envoient une demande de création de commande en précisant, si le client le souhaite, l’identifiant du devis accepté. À ce stade, le middleware ne procède à aucune vérification de la conformité de la commande par rapport au devis précédemment envoyé, il la soumet uniquement aux règles de validation et de rejet de création de commande décrits précédemment.

**Modèle de donnée d’un devis**

- Le modèle de données de l'entité devis est identique à celui de la commande sur le Middleware. La seule distinction réside dans l'ajout de l'attribut « Id quotation », qui permet de référencer le devis de commande dès sa création dans le système.

**Workflow des Statuts du Devis**

La demande de devis suit son propre workflow de statut sur la Standard API. Voici les différents statuts et leurs descriptions :

- Statut "En attente" : Si le devis est généré avec succès et renvoyé au client donneur d'ordre, il est enregistré sous le statut "En attente", car aucun retour n'a encore été reçu concernant l'acceptation ou le refus du devis par le client.
- Statut "Refusé" : Lorsque le client reçoit le devis et décide de ne pas l’accepter, en envoyant une réponse négative, la Standard API traduit cette réponse et met à jour le statut du devis en "Refusé".
- Statut "Accepté" : Si une commande est créée en  incluant l’identifiant d’un devis . Dès la réception de cette demande, la Standard API met à jour le statut du devis référencé sur la demande en "Accepté", avant de procéder au traitement de la demande de commande.

- **Demande acceptée :** Si la référence du devis existe dans le système, la demande de refus est validée et passe à l’étape suivante.

Une fois la référence validée, le middleware vérifie le statut du devis en appliquant les règles suivantes :

- Statut "Refusé" : La demande est rejetée avec un motif précisant que le devis est déjà refusé.
- Statut "Accepté" : La demande est rejetée avec un motif précisant que le devis a déjà été accepté.
- Statut "En attente" : La demande de refus est acceptée.

1. #### <a name="_8v702pj5tkwg"></a>*Authentification des API “WOOP”*
L’intégration du client WOOP repose sur deux flux de données distincts, chacun nécessitant une méthode d’authentification spécifique :
1  ##### <a name="_a9674h6eoybz"></a>*FLux de données entrant (WOOP vers le Middleware) :* 
Dans ce flux, WOOP envoie des données au Middleware XL EDS via des webhooks (également appelés callbacks). Pour recevoir ces données, le Middleware est abonné aux webhooks WOOP en précisant : 

- L’URL API spécifique du Middleware à WOOP
- La clé d’authentification API, transmise dans l’en-tête (HEADER) de chaque requête sous le champ X-API-KEY. Cette clé est unique par environnement et commune à tous les clients (magasins) WOOP.

Les Webhooks (Callbacks), sur lesquelles il faut s’abonner, sont les suivants :

- quote: pour recevoir les demandes de devis
- delivery: pour recevoir les commandes de livraison
- cancelQuote: pour annuler les demandes de devis
- cancelDelivery: pour annuler les commandes de livraison

Plus de détails sur les abonnements aux webhooks sont disponibles dans [la doc officielle WOOP](https://woop.stoplight.io/docs/carrier/1p9vn2atgetp4-subscriptions).
1  ##### <a name="_vda8tm7y2akr"></a>*Flux de données sortant (Middleware vers WOOP) :* 
Dans ce second flux, le Middleware XL EDS envoie les données sur l’API WOOP. L’authentification repose sur l’implémentation d’un client OAuth2 en Grant Type: Client credential.

Les informations du client API sont fournies par WOOP et un seul client est utilisé pour tous les clients (magasins) WOOP.

Plus de détails sur l’authentification API WOOP sont disponibles dans [la doc officielle WOOP](https://woop.stoplight.io/docs/carrier/294f766d547f5-authentication).

Lors du traitement d’une commande sur Urbantz, l’équipe opérationnelle peut, dans certains cas, replanifier la commande ou ajuster son créneau de livraison. Cette mise à jour du créneau est tout d’abord remontée vers le middleware XL EDS, ensuite transmise à WOOP via la requête [Appointment date update](https://woop.stoplight.io/docs/carrier/f144e81925f17-appointment-date-update).


1  ##### <a name="_81iimlpppe9m"></a>*US- Flux Sortant : Envoi du “Créneau affiné”*
Lors du traitement d’une commande sur Urbantz, celle-ci suit un acheminement structuré : elle est d’abord planifiée, puis affectée à une tournée en vue de sa livraison. Cette affectation se matérialise par l’attribution d’un numéro de séquence, définissant l’ordre de livraison de la commande au sein de la tournée en question.

En fonction du numéro de séquence de la commande, que le middleware reçoit depuis Urbantz, celui-ci peut, dans certains cas, générer un créneau horaire affiné. Ce créneau est ensuite transmis à WOOP via la requête [Appointment date update](https://woop.stoplight.io/docs/carrier/f144e81925f17-appointment-date-update).

**Règles de l’envoi du créneau affiné**

L’envoi d’un créneau affiné à WOOP est soumis aux conditions suivantes :

- L’expéditeur auquel appartient le magasin donneur d’ordre de la commande doit avoir le paramètre "Autoriser le raffinement des créneaux horaires" activé dans sa fiche expéditeur (Backoffice).
- Le créneau initial de la commande (celui défini à sa création) doit appartenir à l’une des plages suivantes :
  - De 8h à 20h
  - De 8h à 13h
  - De 13h à 20h
- Si ces deux conditions ne sont pas remplies, aucun créneau affiné ne sera transmis à WOOP.

**Mécanisme de l’envoi du créneau affiné :**

L’envoi du créneau affiné se déclenche selon les règles suivantes :

- Si le créneau initial de la commande ne correspond pas à l’un des trois créneaux mentionnés ci-dessus, alors le créneau affiné n’est ni généré, ni transmis à URBANTZ.
- En cas de modification de la séquence de livraison de la commande (changement de son ordre dans la tournée sur Urbantz), un nouvel envoi du créneau affiné est automatiquement déclenché par le middleware.
- Le créneau affiné est calculé selon :
  - Le créneau de base initial de la commande,
  - Le numéro de séquence de livraison,
  - Les abats définis pour le découpage des créneaux horaires.

*Gestion des EDI Centiro*

**Flux EDI envoyés par Centiro**

Pour chaque commande, deux EDI distincts sont envoyés :

  - Contient des données partielles et incomplètes.
- EDI2 :

  - Contient notamment :

    - les parcelNumber de chaque article de la commande.

- L’EDI2 est soumis aux règles d’acceptation et de rejet des modifications implémentées dans le middleware.

1  ##### <a name="_m4nxf6ndjqcy"></a>*US- Flux entrant/sortant : “Règles de rejets des EDIs CENTIRO”*
**Organisation du serveur SFTP pour les échanges d'EDI avec CENTIRO :**

- L’architecture du serveur SFTP est structurée en deux principaux répertoires :
  - “LIVE” : Espace dédié aux échanges d’EDI, où les fichiers sont déposés par CENTIRO ou le middleware.
  - “ARCHIVE” : Répertoire destiné à l’archivage des EDI après leur interprétation par CENTIRO ou le middleware.
- Chaque répertoire comporte les deux sous dossiers suivants :
  - “SHIPEMENT” : Gère l’envoi des demandes de commandes de CENTIRO vers le middleware pour les créations, les modifications ou les annulations de commandes.
  - “DELIVERY\_STATUSES” : Utilisé pour l’envoi des suivis de livraison du middleware vers CENTIRO pour la mise à jour des statuts des commandes et l’envoi des informations des véhicules.

Cette organisation assure une gestion optimisée des échanges d'EDI, tout en garantissant la traçabilité et la clarté des statuts des fichiers EDI.

**Gestion des EDI entrants (création, modification ou annulation de commandes)**

Pour les rejets des EDIs entrants reçus par CENTIRO, le Principe est le suivant : 

- Rejet de l’EDI (non-conformité des données ou refus pour une raison métier déjà implémentée dans l’API standard) :
  - L’EDI est simplement lu depuis le dossier "SHIPMENTS" sous le répertoire "LIVE", sans aucune action supplémentaire.
- Acceptation de l’EDI (demande validée par le middleware) :
  - L’EDI est lu depuis "LIVE/SHIPMENTS".
  - Il est ensuite instantanément déplacé vers "ARCHIVE/SHIPMENTS" pour archivage.

**Gestion des EDI sortants (Envoi suivi de livraison)**

- En ce qui concerne les rejets des EDIs sortants envoyés à CENTIRO, le Principe est le suivant :
  - Rejet de l’EDI (Statut non interprété par CENTIRO): 
    - CENTIRO ne déplace pas les EDI sortants après leur traitement.
    - Ils restent stockés dans "LIVE/DELIVERY\_STATUSES".
  - Acceptation de l’EDI (Statut interprété par CENTIRO) :
    - L’EDI est lu depuis "LIVE/SHIPMENTS".
    - Il est ensuite instantanément supprimé sans être déplacé vers "ARCHIVE/SHIPMENTS" pour archivage.

- Pour cette raison et afin de garantir une traçabilité systématique de tous les statuts envoyés, le middleware applique une stratégie de double dépôt pour chaque EDI de suivi : 
  - **Dépôt 1** : dans “LIVE/DELIVERY\_STATUSES” → pour traitement par CENTIRO.
  - **Dépôt 2** : dans “ARCHIVE/DELIVERY\_STATUSES” → pour archivage interne, quelle que soit l’issue du traitement (accepté ou rejeté).

1  ##### <a name="_yu6gb3poshfx"></a>*US- Flux Sortant : Envoi des “Informations du véhicules”*
- Une commande sur URBANTZ peut être optimisée à plusieurs reprises et assignée à différentes tournées avant d’être finalement prise en charge. C’est pourquoi, le véhicule affecté à la tournée en cours de livraison n’est transmis à Centiro que lorsque le chauffeur prend effectivement en charge la commande. Cette information est alors envoyée via le composant “vehicleDetail” sur le méme EDI de remontée des statuts de la commande.

- L’information véhicule est transmise via le composant “vehicleDetail”.
- Le “vehicleDetail” est joint à l’EDI de remontée de statuts de la commande.
- Toutefois, le “vehicleDetail” n’est pas inclus dans tous les statuts remontés par le middleware. Il est envoyé uniquement pour les statuts suivants de la commande :
  - Pour les commande “Livraison de marchandise” :
    - 93 : Failed delivery
    - 92 : loaded on delivery truck
  - Pour les commande “Retour de marchandise” :
    - 96 : Customer refusal 
    - 93:2 : Failed pick up
    - 19:2 Pick up at customer

- L’envoi de cette requête inclut les paramètres suivants : 
  - co2Amount : Taux d’émission de carbone, récupéré depuis URBANTZ.
  - vehicle : Type de véhicule ayant effectué la livraison, toujours renseigné comme “TRUCK”.
  - fuelType : Type d’énergie du véhicule. Actuellement, deux valeurs sont transmises à CENTIRO :
    - “ELECTRIC” : pour les véhicules électriques.
    - “DIESEL” : pour tous les autres véhicules.
