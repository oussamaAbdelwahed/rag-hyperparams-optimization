**Règles métiers / Critères d'acceptance :**

- Etant donné que je suis sur l’interface “Création d’un sous-traitant”, lorsque je visualise l’interface alors je peux voir les différents champs suivants :
  - Informations générales : 
  - Champ “Nom” : Champ de saisie libre, Obligatoire.
  - Champ “SIRET” : Champ de saisie libre, Obligatoire.
  - Champ “Code comptabilité” : Champ de saisie libre, Obligatoire.
  - Champ “Identifiant URBANTZ” : Champ de saisie libre, Obligatoire.
  - Champ “N° de téléphone” :  Champ de format N° de téléphone ( +33 et 9 chiffres) Obligatoire.
    - Contact :
  - Champ “Prénom” : Champ de saisie libre, Obligatoire.
  - Champ “Nom” : Champ de saisie libre, Obligatoire.
  - Champ “Fonction” : Champ de saisie libre, Obligatoire.
  - Champ “Adresse email” : Champ de format adresse email, Obligatoire.
  - Champ “N° de téléphone” : Champ de format N° de téléphone ( +33 et 9 chiffres) Optionnel.
- Etant donné que je suis sur l’interface “Création d’un sous-traitant” et que j’ai renseigné correctement tous les champs obligatoires, lorsque je clique sur le bouton “Valider”, alors :
  - Redirection vers l’interface “Listing des sous-traitants”.
  - Affichage d’un toaster de succès avec le message “Le sous-traitant a été créé avec succès.”
  - Création du sous-traitant et ajout dans le listing des sous-traitants.
  - Le sous-traitant est avec le statut “Actif” par défaut.
- Etant donné que je suis sur l’interface “Création d'un sous-traitant” et que je ne renseigne pas tous les champs obligatoires ou que je ne respecte pas le format d’un des champs, lorsque je clique sur le bouton “Valider”, alors :
  - Affichage des champs erronés en rouge avec indication que le champ est manquant ou incorrect.
  - Le nouveau sous-traitant ne se crée pas.
- Etant donné que je suis sur l’interface “Création d'un sous-traitant” et que je renseigne tous les champs pour un nouveau sous-traitant en  lui saisissant le même SIRET qu’un autre sous-traitant déjà créé sur le back-office, lorsque je clique sur le bouton “Valider”, alors :
  - L’utilisateur reste sur la page de création et le sous-traitant n’est pas créé.
  - Affichage d’un message d'erreur sous le champ “SIRET” avec le message “Cet SIRET est déjà utilisé”.
- Etant donné que je suis sur l’interface “Création d'un sous-traitant” et que je renseigne tous les champs pour un nouveau sous-traitant en  lui saisissant le même “Identifiant STT (URBANTZ)”qu’un autre sous-traitant déjà créé sur le back-office, lorsque je clique sur le bouton “Valider”, alors :
  - L’utilisateur reste sur la page de création et le sous-traitant n’est pas créé.
  - Affichage d’un message d'erreur sous le champ “Identifiant STT (URBANTZ)” avec le message “Cet identifiant Urbantz est déjà utilisé”.

1  ##### <a name="_krpe0c30igo8"></a>*US - Création d’une nouvelle grille tarifaire*
**Intitulé / Description :**

En tant que super administrateur du back-office, je souhaite créer une nouvelle grille tarifaire via l’interface du BO.

**Accessibilité :**

Depuis l’interface Listing des grilles tarifaires, accessible via la rubrique Grilles tarifaires sur le menu latéral, je peux cliquer sur le bouton “+ Nouvelle grille tarifaire” pour accéder à l’interface de création d’une nouvelle grille tarifaire.

**Règles métiers / Critères d'acceptance :**

- Organisation de l’interface : L’interface de création est organisée en deux étapes, représentées par un stepper :
  - **Étape 1 :** Informations générales
  - **Étape 2 :** Tarification

⇒ L’utilisateur atterrit, par défaut, sur la première étape **Informations générales**.

- Navigation entre les étapes :
  - **Bouton “Suivant” :** Permet de passer à l’étape suivante.
    1. La navigation libre est restreinte : l’accès à l’étape suivante “Tarification” n’est possible que lorsque tous les champs obligatoires de l’étape en cours sont correctement renseignés. Il est désactivé tant que les données obligatoires ne sont pas renseignées.
    1. Si l’utilisateur a choisi la dimension “Zone”, il est obligatoire d’importer le fichier de zone pour pouvoir cliquer sur “Suivant”.
  - Bouton “**Sauvegarder**” : Permet de sauvegarder les données saisies en mode draft.
###### <a name="_glwon4r0xb2e"></a>*1/- Étape 1 : “Informations générales”*
![](Aspose.Words.2300f782-c12f-46a7-98fd-fcb14a4a3835.007.png)

Lorsque je suis sur l’étape Informations générales, l’interface affiche les éléments suivants :

- **Champs disponibles :**
  - Champ “Expéditeur” :  Champ menu déroulant, obligatoire, qui propose la liste de tous les expéditeurs disponible sur le back-office.
  - Champ “Nom du magasin” : champ menu déroulant, obligatoire, permettant de sélectionner un magasin à associer à la grille tarifaire :
    1. Le champ n’est actif que lorsque l’utilisateur a préalablement sélectionné un expéditeur pour la grille qu’il est en train de renseigner.
    1. La liste déroulante des magasins contient uniquement les magasins rattachés à l’expéditeur sélectionné.
    1. Lorsque l'utilisateur décide de sélectionner un nouvel expéditeur après avoir choisi un magasin, le champ « Nom du magasin » est automatiquement réinitialisé.
  - Champ “Dimension” : champ cases à cocher, obligatoire, permettant de sélectionner jusqu’à deux (2) dimensions au maximum pour la grille tarifaire :
    1. Cinq (5) dimensions sont disponibles : distance, poids, zone géographique, valeur (des articles) et temps.
    1. Lorsqu’un utilisateur sélectionne deux dimensions, les autres options deviennent inactives. En décochant l’une des dimensions sélectionnées, les autres options redeviennent disponibles pour la sélection.
  - Champ “Type de prestation” : champ menu déroulant, obligatoire, permettant de sélectionner une prestation à associer à la grille tarifaire :
    1. Le champ n’est actif que lorsque l’utilisateur a préalablement sélectionné un magasin pour la grille qu’il est en train de renseigner.
    1. La liste déroulante des prestations affichée à l'utilisateur est récupérée à partir des configurations du magasin.
    1. Lorsque l'utilisateur décide de sélectionner un nouveau magasin après avoir choisi une prestation, le champ « Type de prestation » est automatiquement réinitialisé.
  - Champ “Service” : Champ menu déroulant, obligatoire, permettant de sélectionner un service pour la commande. Trois services sont proposés : 
    1. Livraison au Pied du camion
    1. Livraison à la Pièce du choix
    1. Livraison en Point relais
  - Champ “Canal” : Champ de saisie libre, optionnel,  permettant d’indiquer le canal d’achat utilisé par le client final. La valeur de ce champ est spécifique à chaque client. 
  - Champ “Date de démarrage de la grille” : Champ sélecteur de date (Calendrier), obligatoire, permettant de définir la date d’entrée en vigueur de la grille :
    1. Par défaut, l’heure est fixée à 00:00
    1. Seules les dates à partir du jour actuel (inclus) peuvent être sélectionnées. Aucune date antérieure ne peut être choisie.
- **Condition spécifique : Dimension “Zone géographique**”
  - Si l’utilisateur sélectionne la dimension Zone géographique, un bloc supplémentaire apparaît.
  - Bloc “Zones de livraison” :
    1. Texte explicatif : “*Vous avez sélectionné la dimension "Zone géographique". Veuillez importer le fichier de mapping correspondant pour continuer.*”
    1. Bouton “Choisir un fichier” :
       - Position : À gauche du texte explicatif.
       - Icône : Icône d’importation.
       - Fonctionnalité : Permet à l’utilisateur de sélectionner et d’importer un fichier XLSX contenant le mapping des zones.

  1. Tableau des zones de livraison :
     - Structure : Deux colonnes avec “Colonne 1 : Code postal” et la “Colonne 2 : Zone”

Un tableau qui s’adapte automatiquement aux dimensions sélectionnées lors de l’étape précédente :

- Si une seule dimension est sélectionnée : Le tableau comporte 2 colonnes : 
  - La dimension choisie.
  - Le prix correspondant.
- Si deux dimensions sont sélectionnées : Le tableau comporte 3 colonnes : 
  - La première dimension. 
  - La deuxième dimension.
  - Le prix correspondant.

    1. Avec une seule dimension et service "Point relais" : 3 colonnes : Dimension | Prix | Prix point relais
    1. Avec deux dimensions et service "Point relais" : 4 colonnes : Dimension 1 | Dimension 2 | Prix | Prix point relais.

  - Toute ligne ajoutée doit inclure les quantités minimales et maximales.
  - Le prix supplémentaire par article doit être renseigné.
- Services additionnels par article : 
  - Chaque ligne ajoutée doit être entièrement complétée (service, article, unité et valeur).
- Raisons d’échec : 
  - Lorsqu’une raison d’échec est sélectionnée, un prix doit obligatoirement être renseigné.
- Compléments sur les dimensions : 
  - Si un prix est renseigné, le palier correspondant doit être complété.
  - Inversement, un palier ne peut être considéré comme renseigné sans prix associé.


**Contrôle des Champs lors de la Publication d’une Grille**

Le contrôle des champs intervient au moment où l’utilisateur clique sur le bouton “Publier”. Si l’un des champs ne respecte pas les règles définies, plusieurs scénarios peuvent se produire selon l’étape concernée : 

*Scénario 1 : Erreurs dans l’étape “Tarification”*

- Erreurs concernent les champs de la deuxième étape du processus de création de la grille.
- Comportement en cas d’erreur :
  - Le champ erroné devient rouge avec une alerte associée.
  - Un message explicatif spécifique est affiché sur chaque champ concerné.
  - Un scroll automatique repositionne l’interface sur le premier champ en erreur.

*Scénario 2 : Erreurs dans l’étape “Informations Générales”*

- Concerne les champs de la première étape du processus de création de la grille.
- Comportement en cas d’erreur :
  - Redirection automatique vers la première étape.
  - Un message explicatif spécifique est affiché sur chaque champ concerné.

*Scénario 3 : Gestion des erreurs combinées sur les deux étapes*

- Si des erreurs sont présentes à la fois dans la première et la deuxième étape, alors :
  - Priorité au Scénario 1 : l’utilisateur devra d’abord corriger les erreurs de l’étape “Tarification”.
  - Les erreurs de la première étape ne seront pas affichées immédiatement.
  - Une fois les erreurs de la deuxième étape corrigées et que l’utilisateur clique à nouveau sur le bouton “Publier”, le Scénario 2 sera déclenché pour corriger les erreurs restantes sur la première étape.


**Remarque :**

- Pour la gestion des articles obligatoires pour certains expéditeurs, si le magasin concerné appartient à un expéditeur qui gère les articles, alors :
  - Une ligne vide est ajoutée par défaut dans la section “Article”.
- Si l’utilisateur tente de publier la grille sans renseigner cette ligne :
  - Il sera bloqué et une erreur sera affichée sur toute la ligne.
  - Pour bypasser cette erreur et publier la grille sans tarification spécifique aux articles, l’utilisateur doit supprimer cette ligne par défaut avant de cliquer sur le bouton “Publier”.



- Remarque importante : Une grille tarifaire publiée ne peut plus être modifiée. Toute modification nécessitera la création d’une nouvelle grille tarifaire.

1  ##### <a name="_t4anydu161cg"></a>*US- Typologies d’alertes sur le Back-office*
**Typologies des alertes système :**

Le tableau suivant présente toute les typologies d’alerte gérées par le middleware :

|**Type de l’alerte**|**Description**|
| :-: | :-: |
|**Commande nécessitant un hayon**|Alerte notifiant la création d’une commande contenant un colis de plus de 120 kg nécessitant un hayon.|
|**Commande nécessitant la compétence “Passage à 4”**|Alerte notifiant la création d’une commande avec un colis de plus de 90 kg nécessitant la compétence "Passage à 4".|
|**Commande sans sous-traitant**|Alerte notifiant la planification d’une commande sans attribution à un sous-traitant.|
|**Non-retour de commande chez le magasin**|Alerte signalant qu’une commande qui n’a pas été retournée chez le magasin  après un échec de livraison ou une annulation client.|

|**Échec de chargement (Faute XL EDS)**|<p>Alerte notifiant un échec de chargement d’une commande pour l’une des raisons suivantes :</p><p>- Camion non adapté</p><p>- Panne</p><p>- Force majeure</p><p>- Accident</p>|

|**Rejet de création de commande : Créneaux non valides**|Alerte signalant le **rejet** d’une demande de création de commande en raison de **créneaux de livraison incorrects**.|
|**Début d’un créneau EXPRESS**|Alerte notifiant le Début d’un créneau EXPRESS pour un magasin qui comporte le paramètre “Alerting EXPRESS” activé et où des commandes ont été créées.|
|**Ajout de “Bonus”/”Malus”**|Alerte signalant l'ajout d'un bonus ou l'application d'un malus dès leur enregistrement sur une commande spécifique.|
|**Centiro : rejet de création des commandes**|Alerte récapitulant les commandes dont la création a été refusée en raison d'une non-conformité des données ou du non-respect d'une règle métier déjà implémentée dans l'API standard.|
|**Adresse Collecte pas dans le carnet des adresses du magasin**|Alerte notifiant la création d’une commande splittée en 2 tâches avec une adresse de collecte absente du carnet d'adresses du magasin donneur d’ordre sur le Back Office.|


**Règles métiers / Critères d'acceptance :**

*1/- Alerte du type “Commande nécessitant un hayon”*

- **Scénario déclenchant l’alerte :** l’alerte se déclenche lorsqu’une nouvelle commande est créée sur le middleware, quelle que soit sa source (API, WOOP, CENTIRO ou Portail), qu’elle passe avec succès toutes les validations et règles de rejet, et que le champ “**Hayon**” est défini sur “**OUI**”.

*2/- Alerte du type “Commande nécessitant la compétence “Passage à 4”*

- **Scénario déclenchant l’alerte :** Lorsqu’une nouvelle commande est créée sur le middleware, quelle que soit sa source, qu’elle passe avec succès toutes les validations et règles de rejet, et qu’elle inclut le service “Passage à 4” parmi ses services additionnels.

*3/- Alerte du type “Commande sans sous-traitant”*

- **Scénario déclenchant l’alerte :** Lorsqu’une commande passe du statut “**Annoncée**” à “**Planning validé**”, et que le champ “Sous-traitant” reste **vide**.

*4/- Alerte du type “Non-retour de commande chez le client”*

- **Scénario déclenchant l’alerte :** l’alerte se déclenche au moment où une commande respecte les conditions suivantes : 
  - Le statut de la commande est l’un des statuts suivants :
    - “Échec de livraison”.
    - “Annulation client après chargement”.
  - Le livreur a répondu “**NON**” à la question “Est-ce que tu as retourné la marchandise au magasin ?” sur son PDA avant de clôturer la tournée.

*5/- Alerte du type “Retard de planification de commande”*

- **Scénario déclenchant l’alerte :** Lorsqu’une commande est en statut “**Annoncée**” et que l’heure du cut-off est dépassée de **1h30.**
- **Mécanisme de déclenchement de l’alerte :** Un cron job s’exécute toutes les 15 minutes pour détecter les commandes non planifiées dans les délais.

*6/- Alerte du type “Retard de livraison”*

- **Scénario déclenchant l’alerte :** l’alerte se déclenche au moment où une commande respecte les conditions suivantes : 
  - Le statut de la commande est l’un des statuts suivants : 
    - “Créée”
    - “Annoncée”
    - “Planning validé”
  - L’heure de début du créneau de livraison est dépassée de 30 minutes.
- **Mécanisme de déclenchement de l’alerte :** Un cron job s’exécute toutes les 15 minutes pour identifier les commandes en retard de livraison.

*7/- Alerte du type “Échec de chargement (Faute XL EDS)”*

- **Scénario déclenchant l’alerte :**  l’alerte se déclenche au moment où une commande respecte les règles suivantes : 
  - Passe du statut “Planning validé” au statut “Échec de chargement”
  - La raison d’échec est l’une des raisons suivantes
    - “Camion non adapté”
    - “Panne”
    - “Force majeure”
    - “Accident”

*8/- Alerte du type “Annulation après chargement”*

- **Scénario déclenchant l’alerte :**  l’alerte se déclenche au moment où le middleware reçoit une demande d’annulation de commande, qu’elle est acceptée et qu’elle vient après le chargement de la commande par le livreur.

*9/- Alerte du type “Indice CNR (M-1) manquant”*

- **Scénario déclenchant l’alerte :** Lorsqu’un indice CNR (M-1) nécessaire au calcul de la surcharge des commandes en statut “Facturable” est absent du listing des indices CNR. 
- **Mécanisme de déclenchement de l’alerte :** Un cron job s’exécute le **1er jour de chaque mois** à **00:00** pour détecter les catégories CNR ayant des indices manquants.
- Toutes les Catégorie CNR seront consolidées sur une même alerte.

*10/- Alerte du type “Rejet de création de commande : Créneaux non valides”*

- **Scénario déclenchant l’alerte :**  l’alerte se déclenche au moment où une demande de création d’une nouvelle commande est reçues par le middleware, indépendamment de sa source de création (API, WOOP, CENTIRO ou Portail), et qu’elle est rejetée suite à la raison de rejet suivante :
  - “DELIVERY\_TIME\_WINDOW\_INVALID”

*11/- Alerte du type “Début d’un créneau EXPRESS”*

- **Scénario déclenchant l’alerte :** l’alerte se déclenche au moment où un créneau EXPRESS, pour un magasin qui a le paramètre “Alerting EXPRESS” activé sur ses configurations sur le backoffice, démarre et qu’il comporte au moins une commande créée pour un magasin donné. 
- **Mécanisme de déclenchement de l’alerte :** Un Cron job est implémenté sur le système pour parcourir toutes les commandes toutes les 15min et qui permettra de détecter les commandes en prestation EXPRESS dont leur créneau de livraison a démarré appartenant à un magasin sur lequel l’alerting EXPRESS est activé.
- Toutes les commandes d’un même magasin et d’un même créneau EXPRESS sont regroupées dans une seule alerte.

*12/- Alerte du type “Ajout de “Bonus”/”Malus””*

- **Scénario déclenchant l’alerte :** L’alerte est générée lorsqu’une commande subit une modification de son “Bonus” ou de son “Malus” sur au moins l’une de ses tentatives de livraison. Cette modification peut résulter soit de l’ajout d’un bonus, soit de l’application d’un malus. 

*13/- Alerte du type “CENTIRO : rejet de création des commandes””*

- **Scénario déclenchant l’alerte :** Lorsqu’une ou plusieurs demandes de création de commandes sont rejetées par le middleware en raison d'une non-conformité des données ou du non-respect d'une règle métier déjà implémentée dans l'API standard.
- `  `**Mécanisme de déclenchement de l’alerte :** Un **cron job** s’exécute **quotidiennement à une heure précise** (18:00) pour détecter les demandes concernées.
- Toutes les commandes seront regroupées dans une même alerte par jour. 

*14/- Alerte du type “Adresse de Collecte pas dans le carnet d’adresses du magasin”*

- **Scénario déclenchant l’alerte :**  l’alerte se déclenche au moment où le middleware reçoit une demande de création d’une commande de type “Delivery”, qu’elle est acceptée et qu’elle comporte une adresse de collecte qui ne correspond à aucune adresse enregistrée dans le carnet d’adresses du magasin donneur d’ordre.
- **Remarque** : Cette alerte est déclenchée uniquement pour la première commande reçue de chaque magasin remplissant ces conditions.
